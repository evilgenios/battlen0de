# Warpath platform — service (stage 1/2/3)

This is the extracted, multi-account-capable Warpath protocol engine plus
the persistence and API layers built on top of it. It came out of the
original single-file Discord bot (`warpath_bot.py`, still preserved
unchanged at its original location — see the top-level README).

Stage 1/2/3 scope: protocol engine + AccountSession/AccountManager (proven
with real concurrency), PostgreSQL/Neon persistence, and a FastAPI service
around AccountManager. No Next.js dashboard, no deployment, and the legacy
Discord bot still isn't re-pointed at any of this — that's Stage 4+.

## Layout

```
service/
  app/
    main.py                 FastAPI app + the ONE process-wide AccountManager
    deps.py                 get_repository/get_account_manager/get_current_user/get_owned_account
    core/
      warpath/
        credentials.py       WarpathCredentials — one account's identity/device/gateway config
        protocol.py           AES/varint/protobuf wire-format helpers (unchanged)
        connection.py          WarpathConnection — one account's TCP client
        lilith.py               Lilith account-linking HTTP client
        protobuf/                generated *_pb2.py files, byte-identical to the original export
      account_session.py    AccountSession — one account's lifecycle + thread
      account_manager.py    AccountManager — the registry of all sessions
    db/
      models.py              SQLAlchemy models (users, warpath_accounts, account_snapshots,
                              discord_links, account_events)
      session.py              engine/session-factory from DATABASE_URL
      repository.py            AccountRepository (Protocol) + SqlAlchemyAccountRepository —
                                the only place that issues SQLAlchemy queries
    security/
      crypto.py               encrypt_secret()/decrypt_secret() (Fernet, WARPATH_ENCRYPTION_KEY)
    schemas/
      accounts.py, sessions.py, actions.py    Pydantic request/response models
    api/
      accounts.py              GET/POST /accounts, GET/DELETE /accounts/{id}
      sessions.py               connect/disconnect/reconnect/status
      actions.py                 collect/scan/farm/recall/scout
      events.py                   GET /accounts/{id}/events
  migrations/                Alembic (env.py reads DATABASE_URL; migrations/versions/0001_initial_schema.py)
  scripts/
    dev_two_accounts.py           Stage 1/2 manual concurrency test (still works, untouched)
    migrate_json_accounts.py      ONE-TIME warpath_accounts.json -> Postgres migration
  tests/                    pytest suite — see "Running the tests" below
```

## Running the service

```bash
../.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Requires `DATABASE_URL` and `WARPATH_ENCRYPTION_KEY`. Production defaults to
`APP_ENV=production`, `AUTH_MODE=session`, `DASHBOARD_COOKIE_SECURE=true`.
Every product API requires a password session **even before any password
users exist**. Anonymous requests return 401. `/health` is public and is
only a status hint, never an authorization switch.

Provision users explicitly (operator action, writes the configured DB):

```bash
python scripts/bootstrap_dashboard_admins.py --email operator@example.com --role admin
python scripts/bootstrap_dashboard_admins.py --email player@example.com --role member
```

The script prompts for passwords; no signup or billing was added. Null,
unknown, or incorrectly cased roles cannot log in. Existing password users
with missing roles need an explicit role assigned by the operator. Members
can access only accounts they own. Explicit admins retain cross-owner
operator access by account ID; `/accounts` lists the caller's own accounts
for both roles. Manual credential/gateway import, diagnostics and all
mass-deploy operations (preview, execution, cancellation) require admin.
All session-authenticated writes, including logout, require the session's
CSRF cookie/header pair.

For isolated local development ONLY, bind to `127.0.0.1` and set
`APP_ENV=development`, `AUTH_MODE=local`, `DEV_USER_EMAIL=dev@example.com`,
`DEV_USER_ROLE=member`, `DASHBOARD_COOKIE_SECURE=false`. Explicitly select
`DEV_USER_ROLE=admin` if testing internal tools. Tests use `APP_ENV=test`.
Production rejects local mode/insecure cookies at startup. Merely setting
`DEV_USER_EMAIL` does nothing in session mode; a stale cookie never falls
back to a local identity. `/auth/me` reports the explicit local identity.

**Exactly one worker and one replica are required.** Website sessions,
revocation, grants and throttles now persist in PostgreSQL. AccountManager,
game connections, linking challenges, lifecycle serialization and the
mass-deploy lock remain process-local. A restart preserves valid website
sessions, discards pending linking challenges and interrupts game sessions.
Phase 6 rejects `AUTOSTART_ACTIVE_ACCOUNTS=true` (and unknown values).
An explicit admin observation grant is required before Connect; grants expire
in at most 60 minutes and disappear on disconnect/restart. No automatic
reconnect or game-changing/automatic actions are enabled while upstream evidence
is unverified. Owner status/capacity and global capacity still apply.
Never run mixed application versions or multiple workers. See
[pilot activation contract](../docs/PHASE6_ACTIVATION.md) and
[operator procedures](../docs/PILOT_OPERATIONS.md) for the authenticated APIs.
There is no environment evidence override or public activation/signup.

Read [Phase 3 migration contract](../docs/PHASE3_MIGRATION.md) **before**
upgrading. Stop the worker, back up, reconcile duplicate canonical identities
offline, run `alembic upgrade head`, then start the new version. Migration
never chooses an owner or merges accounts. Malformed legacy game identities
become `needs_reauth`; NULL/invalid website roles remain blocked. Old memory
cookies cannot be migrated, so the upgrade requires one fresh website login.

### Pilot identity and website sessions

Bootstrap the first administrator with the explicit CLI above. Thereafter,
an admin uses Settings → Pilot provisioning (or `POST /auth/pilot/grants`)
to issue a member invitation or recovery token. Verify the recipient and
deliver the token privately. No email is sent and no public signup exists.
The recipient pastes the token at `/activate`; never put tokens in URLs.
Invitations expire after 48 hours; recovery after one hour. Issuing a new
grant invalidates earlier grants for that identity. Redemption is atomic,
preserves an existing valid recovery role, revokes all website sessions,
and requires a fresh login. Disabled users and legacy invalid roles require
explicit operator review, not a recovery-based privilege grant.

Website bearer tokens are random and stored only as SHA-256 hashes. Sessions
expire after 24 hours absolute or two hours idle. Authentication checks the
current user's role, status and credential version on every request. The
bootstrap password command increments the version too. Website session
revocation does **not** disconnect games: these are independent sessions.
Settings lists/revokes the caller's sessions; `POST /auth/revoke-all` revokes
all of that identity's sessions. Public session IDs in the inventory are
cache namespaces, never authentication credentials. No database outage
falls back to memory or local authentication.

Defaults per user: five linked game accounts, five website sessions, two
active game accounts. Successful login at the website-session cap revokes
the oldest session, so a lost browser cannot lock out a password holder.
Account creation enforces its cap under a PostgreSQL user-row lock. The
single-worker lifecycle lock serializes game actions with status changes,
connect/reconnect, deletion and relink. Admin-only
`POST /auth/pilot/users/{user_id}/policy` accepts `status` (`active` or
`disabled`), `max_accounts`, `max_sessions`, and `max_active_accounts`.
Policy updates revoke browser sessions and stop all that user's game
sessions; lowering an account cap preserves existing rows and blocks new
ones. It never assigns a role. Limits also apply to admins.

### Linking, relinking and account status

Email linking requires isolated operator `WARPATH_APP_UID` and
`WARPATH_APP_TOKEN` (server-only; never `NEXT_PUBLIC_*`). No customer's
credentials are selected. The complete trusted device/client template in
`.env.example` is validated **before sending a code**, captured on the
challenge and reused at verification. Members cannot submit gateway or
client metadata. Missing/invalid configuration returns 503.

Challenges remain owner-bound, including for admins. Resend with
`POST /accounts/link/request` and the original `challenge_id`, email and
optional `account_id`. Delete via `DELETE /accounts/link/{challenge_id}`.
Foreign/expired challenges return 410; a busy challenge returns 409. There
are at most three pending challenges per owner. Verification is atomically
claimed and a successful upstream result consumes the challenge before
persistence; after a DB conflict/failure, request a fresh code. Codes are
never persisted or logged. Do not enable request/response body capture in
application logs, database query logging, ingress logs or external tracing.

The canonical `warpath:lilith:<decimal app_uid without leading zeroes>` is
unique globally, independent of email/platform/gateway/profile UID. This
models the Lilith identity returned by the existing protocol; it does not
claim support for multiple characters under one Lilith identity. Linking a
duplicate never transfers ownership or silently replaces credentials.
Relink through an account's link or supply `account_id` when requesting a
code. Only that account's owner may relink (no admin override), the game
session must be inactive, and the proved identity must match. Relinking a
legacy malformed identity is possible once, subject to uniqueness. The
existing row ID, ownership, label and history are retained.

Only persisted `active` accounts with active owners can start or issue game
actions. Other states allow reads, disconnect and deletion. Admin-only
`POST /accounts/{account_id}/status` changes status and stops a blocked
account's live session. `needs_reauth` permits owner relink; `disabled` and
`restricted` do not. Authentication failure/restriction events persist
`needs_reauth`/`restricted`. Admin status changes are explicit; relinking
cannot bypass a restriction. Mass-deploy execution rechecks policy for each
account and cancellation remains independently admin-only.

### Throttles and retention

Fixed-window PostgreSQL counters survive restart: login 60/minute per
network peer and 5/15 minutes per normalized email; token redemption
30/minute per peer and 5/15 minutes per token digest; linking sends 3/minute
and 10/hour per website user; verification 30/5 minutes per user plus the
challenge's five-attempt limit; grant issuance 20/hour per admin. Responses
include HTTP 429 and Retry-After. Counter keys hash identifiers; they do not
store plaintext emails, tokens or peer addresses. No production bypass flag.
The actual network peer is used; forwarded headers are not trusted. Behind
Next.js, the peer bucket is shared. Trusted ingress identity, tuning and
edge abuse protection remain deployment/public-launch gates.

The snapshot maintenance task also removes throttle buckets older than one
day and sessions/grants expired for seven days. Revoked/expired credentials
are rejected immediately regardless of cleanup. Keep the interval positive.

See [Phase 3 handoff](../docs/PHASE3_HANDOFF.md) for exact verification and
remaining launch gates.

## Migrating from the legacy bot's warpath_accounts.json

```bash
../.venv/Scripts/python.exe scripts/migrate_json_accounts.py \
  --json-path ../../warpath-audit/ughhhh/warpath_accounts.json \
  --env-file ../../warpath-audit/ughhhh/.env \
  --owner-email you@example.com \
  --dry-run
```

Drop `--dry-run` to actually write. See the script's module docstring for
`--force` (update instead of skip on a duplicate) and why `--env-file`
matters. It never prints `app_token`/`device_id` and never modifies the
source JSON file.

## Proving two real accounts run concurrently (Stage 1/2, still works)

1. Copy `scripts/.env.two_accounts.example` to `scripts/.env.two_accounts`
   and fill in real `WARPATH_A_*` / `WARPATH_B_*` values for two accounts
   you control (never commit this file — it's gitignored).
2. From `service/`: `../.venv/Scripts/python.exe scripts/dev_two_accounts.py`
3. Watch the event log — both accounts reach `connected` independently,
   with two distinct sockets/threads. `Ctrl+C` stops both cleanly.

## Phase 4: farming and collection replies

Read [Phase 4 handoff](../docs/PHASE4_HANDOFF.md) for correlation constraints,
verification results and the next phase. No database migration is introduced.
Existing Phase 3 migration, revocation, ownership and one-worker requirements
still apply.

`POST /accounts/{id}/collect` now returns `status` (`confirmed`, `partial`,
`uncertain`, `rejected`), `detail`, and `unconfirmed_building_ids`, alongside
its existing counters. Only correlated replies contribute to `items_gained`;
that legacy counter measures **reward entries, not resource quantities**.
An uncertain zero is not proof that buildings were empty.

`POST /accounts/{id}/farm` returns `status` (`confirmed`, `uncertain`,
`rejected`, `not_dispatched`). `dispatched=true` requires a matching reply
with the requested vehicle/mine and a traveling/gathering state. Timeout,
connection closure or cancellation of a wait cannot establish failure of a
command already sent. Pending trucks/buildings remain reserved; overlapping
attempts return 409 or no available truck. No automatic retry is introduced.

Matching requires `down.msg_seq_id` to echo the request sequence. The schema
supports that field, but **live echo semantics have not been verified** for
these actions. Missing/mismatched sequences remain uncertain. Do not enable
customer farming/collection until authorized protocol evidence establishes
that contract. The synthetic fixtures deliberately assert the proposed
contract; they are not evidence of upstream behavior.

## Phase 5: pilot command observations

`GET /accounts/{id}/command-status` is an owner/admin-authorized, no-store,
read-only projection of the current connection tracker. It shows unresolved
requests/reservations and up to 50 completed search/collect/gather observations,
including matching late replies. It exposes no raw replies, wire sequence IDs,
credentials or socket metadata and sends no game request. Reads remain available
for restricted/disconnected accounts under the existing ownership policy.

History is always incomplete across reconnect/restart; an empty report does
not resolve older commands. A new `observation_id` identifies a new tracker,
not an upstream idempotency guarantee. Tracking capacity remains 1,024 tickets.
No force-clear/retry/reconcile mutation was introduced. Existing Phase 4
confirmation and release rules still apply. No database/environment migration.

Read [confirmation evidence](../docs/COMMAND_CONFIRMATION_EVIDENCE.md),
[pilot procedures](../docs/PILOT_OPERATIONS.md) and the

unverified; these safeguards do not authorize public launch or game execution.
